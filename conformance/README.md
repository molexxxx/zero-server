# Conformance

The files in this directory are the contract every language binding is held to.
Each is generated; edit the generator and regenerate rather than the file.

## vectors.json

Generated by `cargo run -p zero-examples --example conformance_vectors` and
committed. Each outcome comes from the Rust crate that implements the section,
and where a case states the outcome a specification requires, the generator
compares the two before it writes the file, so it fails rather than write a
vector the crates disagree with.

### Runners

- The generator itself, over `zero-http1` and its response writer,
  `zero-router`, `zero-ws` with the server's SHA-1, `zero-sse`, `zero-qpack`
  and `zero-h3`.
- The CI check "Examples run and the conformance vectors are current" in
  `.github/workflows/ci.yml`, which runs the generator and fails when the
  committed file differs from its output.

No binding asserts the file yet. The .NET smoke project copies it next to its
executable but does not read it. A binding's runner joins this list when it
exists, and it must refuse a section it does not know, so a section cannot pass
unread.

### Shape

One JSON object with sorted keys:

- `note`: the sentence saying which program wrote the file.
- `tolerance`: the absolute tolerance a binding uses when it compares a floating
  point field, because accumulation order differs between languages.
- one section per capability, keyed in camelCase: `http1Parser`,
  `responseSplitting`, `router`, `ws`, `sse`, `qpack` and `h3Frames`. Inside a
  section, byte fields are lowercase hex strings, numbers are JSON numbers with
  `f32` widened to `f64`, integers that can exceed 2^53-1 (the 62-bit QUIC and
  QPACK values) are decimal strings, and a list of cases is an array of objects
  with the same fields in each.

The `router` section holds one route table and requests against it. A case's
`expect` is a match (`id`, `params`, `path`, `query`, `head`) or a `status`,
with `allow` for 405 and for the automatic OPTIONS answer. PATCH is a method
with its own route slot (RFC 5789). `PROPFIND` is an unimplemented token: the
router answers it 501, and over HTTP/1.1 the request parser already answers it
501 and closes the connection, because it is longer than every implemented
method; `MKCOL` reaches the router.

Each `ws` case has `name`, `section`, `kind`, `request` (the opening handshake),
`routeProtocols` and `routeOrigins` (the route's subprotocols, and its Origin
allow list or `null`), `clientFrames` and `expect`:

- `handshake`: `clientFrames` is empty and `expect` is the response `status`
  to a GET on the WebSocket route, with the WebSocket `fields` it carries:
  `Upgrade`, `Connection`, `Sec-WebSocket-Accept` and the chosen
  `Sec-WebSocket-Protocol` on a 101, and `Sec-WebSocket-Version` on a 426.
- `frames` and `close`: `request` is an accepted handshake and `clientFrames` the
  masked frames sent after it. `expect` lists the `events` the server reports
  (`type`, `data` in hex, and `code` for a close), the `serverFrames` it sends
  on its own (pongs and Close frames), the code the connection `failed` with or
  `null`, and whether the connection is `finished` once those frames are
  written.

Each `sse` case has `name`, `section`, `call` and `expect`. A `call` is an event
(`data`, with `event` and `id` when present), a `comment`, or a `retry` in
milliseconds; a comment is written as one comment line per line of its text.
`expect` is the stream `bytes` the call writes, or `rejected` when the call is
refused and writes nothing.

Every case is built with library calls in the generator, never pasted as a byte
blob, and the published vectors of a specification are preferred where they
exist (RFC 7541 Appendix C for HPACK, RFC 9204 Appendix B for QPACK, the RFC
6455 Section 1.3 key and accept value, the WHATWG HTML Section 9.2.6 multi-line
data example).

## api-surface.json

Generated from the public exports and JSDoc of `@zero-server/sdk` 1.1.0, read
from the commit npm records for that version (`source.gitHead` in the file), and
copied here; it is never edited by hand. Every export has one canonical id, `<scope>.<snake_case>`, and a kind:

- `ffi`: carried by the C ABI of `zero-ffi` and reached through the generated
  declarations of every binding (`include/zero.h`, `index.d.ts`, `__init__.pyi`,
  the `[LibraryImport]` mirror).
- `facade`: written in each binding language over the ABI, keeping the shape the
  Node SDK gave it.
- `host-only`: a class that stays in the host language, such as a Model class or
  an error class, checked by a per-binding export test rather than by the header
  diff.

Each export also records its `status` (`kept`, `shim` for the cluster helpers
that survive as a host-side shim, or `dropped` with the reason), the `release`
whose contract tier first carries it, and the summary, parameters and return
documented in the SDK. The canonical ids let each binding's generated
declarations be compared with this file without a literal name comparison
across naming conventions; no CI step makes that comparison yet.

`api-surface.node.json`, `api-surface.python.json` and `api-surface.dotnet.json`
hold each binding's naming rules and the spelling of every canonical id in that
language: the Node SDK name unchanged, snake_case functions with PascalCase
classes in Python, and PascalCase everywhere in C# with error classes ending in
`Exception`.

`api-surface.members.json` lists the members of the classes the facade keeps
(`App`, `Router`, `Request`, `Response`, `SSEStream`, `WebSocketConnection` and
`WebSocketPool`), read from the `types/*.d.ts` files of the same commit: each
property with its type and whether it is optional or read-only, and each method
with its overloads.

## regressions.md

The catalog of open defects carried over from the zero-server audit, each
becoming a failing-first test in the crate that owns the behavior. It is
gitignored and kept locally until it is empty.
